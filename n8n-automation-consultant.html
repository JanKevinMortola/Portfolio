I focus on workflow reliability, not just node connections

A workflow that succeeds during one test is not necessarily production-ready. I think through missing data, duplicate events, unexpected API responses, timing issues, authentication failures, manual-review conditions, exception states, and what the business should see when something goes wrong.

Typical engagements

  • Fix a broken workflow: identify the root cause, correct the logic or mapping, test the full path, and explain what changed.
  • Build a new workflow: map the process, define the source of truth, connect the required systems, and test normal and exception paths.
  • Improve an existing automation: reduce duplicate work, simplify logic, improve error handling, and make the workflow easier to maintain.
  • Operations system design: connect n8n to a broader operating model involving ClickUp, Google Workspace, forms, reporting, approvals, and human review.

How I approach testing

I test the workflow from the business outcome backward. That includes happy-path execution, missing or malformed inputs, duplicate submissions, API failures, branching logic, field mapping, expected status changes, and whether the final output is understandable to the person who actually operates the process.
